# Access Policy page wired to real backend API

This change replaces the mock data layer for the Access Policies feature with real API calls, adds a dedicated backend handler through the service layer (matching the pattern of other entity handlers), and introduces inline entity creation during policy save. The frontend gains a metadata panel, delete confirmation dialog, search/pagination on the list page, and tags are migrated from `string[]` to `FormTag[]` (key-value pairs).

Watch for:
- **Partial entity creation with no rollback** (confirmed) — `createPolicy` creates sub-entities sequentially with no compensation logic; a failure mid-way leaves orphaned entities in the database.
- **N+1 queries on policy list** (confirmed) — `loadJunctions` is called per-row inside `List()`, issuing 3 additional queries per policy.
- **Race condition in `handleAddExisting`** (confirmed) — state is updated optimistically (mode change) before the async fetch resolves, and the `.then()` closure captures a stale `values` reference.
- **No transaction boundary in repository Create/Update** (confirmed) — the main INSERT/UPDATE and junction sync are separate statements without a transaction, so a crash between them leaves inconsistent data.

## High-level view

The backend gains a proper service+handler layer for access policies, following the same pattern as client workloads and trust providers. The handler parses DTOs, delegates to `AccessPolicyService`, which validates and calls the repository. The repository now loads junction tables (trust providers, credential providers, access conditions) for every list item, which is correct for data completeness but introduces an N+1 performance concern at scale.

On the frontend, the mock data layer is fully replaced by `apiClient` calls. The `fetchPolicy` function hydrates all related entities in parallel (good), but `createPolicy` performs sequential inline entity creation with no rollback strategy. The `PoliciesPage` fetches five additional entity lists to resolve names in columns — a practical approach for now, capped at 100 items per list, but will need a server-side join or BFF once entity counts grow past that.

The `tags` type change from `string[]` to `FormTag[]` is a breaking interface change that touches the form, the API serialization, and the detail components. The migration appears complete across all touched files.

<summary>Issues (7)</summary>

1. **No rollback on partial inline creation** — `createPolicy` creates client workloads, server workloads, trust providers, access conditions, and credential providers sequentially. If step 4 fails, steps 1-3 leave orphaned entities. Add compensation logic (delete created entities on failure) or wrap in a backend endpoint that does all creation atomically.
2. **N+1 junction loading in List** — Each policy in the list triggers 3 separate queries via `loadJunctions`. For a page of 25 policies, that's 75 extra queries. Use a batch query or a JOIN to load all junctions in one pass.
3. **Stale closure in handleAddExisting** — In `TrustProviderTab` and `AccessConditionTab`, `handleAddExisting` calls `setMode('new')` synchronously and then reads `values` inside a `.then()` callback. If React re-renders between the click and the promise resolution, the closure may reference stale `values`. Capture the current values before the async call, or use `useRef` for the latest value.
4. **No transaction in repository Create/Update** — The access policy INSERT and the junction sync (3 DELETEs + N INSERTs) run as separate pool calls. A crash or connection drop between them leaves the policy without its relations. Wrap in `pool.Begin()`/`tx.Commit()`.
5. **ILIKE wildcard injection** — The `%` and `_` characters in search input are not escaped before being concatenated inside the ILIKE pattern. A user searching for `%` would match all rows. Escape `%` → `\%` and `_` → `\_` in the Go layer before passing to SQL.
6. **100-item ceiling on name resolution** — `PoliciesPage` fetches entity names with `perPage: 100`. Tenants with more than 100 of any entity type will show "—" for unresolved names. Consider resolving names server-side in the list response.
7. **Update returns stale junction data** — `Update` calls `QueryRow(...).Scan(&p.CreatedAt, &p.UpdatedAt)` but never reloads junctions into `p`. The response DTO serialized from `p` will have whatever junction data the caller passed in, which may be stale if other processes modified junctions concurrently.

## Inline entity creation and partial failure

`createPolicy` in `policiesApi.ts` creates entities one at a time:

```typescript
let clientWorkloadId = values.clientWorkloadId
if (!clientWorkloadId && values.client.name) {
  const cw = await apiClient.post<{ id: string }>('/client-workloads', { ... })
  clientWorkloadId = cw.id
}
// ... repeat for server, trust providers (loop), conditions (loop), credential
await apiClient.post<PolicyDTO>(BASE, { ... })
```

If the trust provider loop fails on the second item, the first trust provider and the client/server workloads are already persisted with no reference to any policy. The user sees an error, retries, and now has duplicate orphaned entities. This is the biggest data integrity gap in the change.

Two paths to fix: (a) expose a single backend endpoint that accepts inline entity specs and creates everything transactionally, or (b) add client-side compensation — catch the error, attempt to delete already-created entities, and surface a clear message about what was cleaned up vs. what leaked.

## N+1 queries on policy list

The diff adds `loadJunctions` inside the `List()` loop:

```go
for rows.Next() {
    // ... scan ...
    if err := r.loadJunctions(ctx, &p); err != nil {
        return nil, 0, err
    }
}
```

`loadJunctions` issues 3 queries (trust providers, credential providers, access conditions) per policy. For a page of 25, that's 75 additional round-trips to Postgres. Other entity repositories (client workloads, trust providers) don't have this problem because they only have a single computed `policy_count` subquery.

Fix: collect all policy IDs from the page, then batch-load junctions with `WHERE policy_id = ANY($1)` in 3 queries total, then assign results back.

## Race condition in handleAddExisting callbacks

In `TrustProviderTab.handleAddExisting`:

```typescript
function handleAddExisting(id: string) {
  if (!selectedIds.includes(id)) onToggleId(id)
  fetchTrustProvider(id)
    .then((tp) => {
      onChange([...values, { /* ... */ }])  // `values` is captured at call time
    })
    .catch(() => {
      onChange([...values, { ...EMPTY_TRUST_PROVIDER }])
    })
  setMode('new')  // triggers re-render immediately
}
```

`setMode('new')` causes a synchronous re-render. When the promise resolves, the `values` variable inside the closure is from the render that existed at the time `handleAddExisting` was called, not the current render. If the user added another provider between the click and the fetch resolution, that addition would be overwritten. The same pattern exists in `AccessConditionTab`.

## Repository lacks transaction boundaries

```go
func (r *AccessPolicyRepo) Create(ctx context.Context, tenantID uuid.UUID, p *domain.AccessPolicy) error {
    // 1. INSERT access_policies (single statement)
    err := r.pool.QueryRow(ctx, `INSERT INTO access_policies ...`).Scan(...)
    // 2. sync junction tables (3 DELETEs + N INSERTs, each a separate Exec)
    if err := r.syncJunctions(ctx, p); err != nil {
        return err
    }
}
```

If the process crashes after step 1 but before `syncJunctions` completes, the policy exists without its trust providers or credential providers. Similarly, `syncJunctions` deletes all existing junctions before re-inserting, so a partial failure there leaves the policy with no associations at all. Both Create and Update should wrap the entire operation in a transaction.

## ILIKE wildcard characters not escaped

The search query uses:
```sql
WHERE ... name ILIKE '%' || $2 || '%'
```

PostgreSQL's `ILIKE` treats `%` as "any sequence" and `_` as "any single character" inside the pattern. Since `$2` is the raw user search string, a search for `100%` matches any name containing `100` followed by anything (which is all of them). This isn't a security issue (it's parameterized, not injectable), but it's a correctness bug for certain search terms. Fix: escape `%` and `_` in the search string before passing to the query, or use a pattern-free approach like `position(lower($2) in lower(name)) > 0`.

## Update response returns caller-provided junction data

The `Update` handler does:
```go
p, _ := req.toDomain()
p.ID = id
if err := h.svc.Update(r.Context(), tenantID, &p); err != nil { ... }
respondJSON(w, http.StatusOK, toAccessPolicyResponse(&p))
```

After `Update`, `p.TrustProviderIDs` etc. contain whatever the caller sent in the request — not what's actually in the database after `syncJunctions`. If `syncJunctions` silently skipped an invalid UUID (which it does — unparseable UUIDs are simply dropped in `toDomain`), the response would claim those IDs are associated when they're not. The fix is to reload the policy from the database after update (like `GetByID`) before building the response.

## PoliciesPage name resolution ceiling

```typescript
const { data: cwData } = useQuery({
  queryKey: ['client-workloads', 'names'],
  queryFn: () => fetchClientWorkloads({ perPage: 100 }),
  staleTime: 60_000,
})
```

This caps at 100 items. Any policy referencing a workload beyond the first 100 (by creation order) will show "—" in the table. The `staleTime: 60_000` means stale data persists for a minute even after entity creation. Consider adding an API that returns just `{id, name}` pairs for all entities in a tenant, or include resolved names in the policy list response server-side.
